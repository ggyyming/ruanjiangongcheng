### 共用上传配置

A 和 C 使用以下依赖及路径，各自维护本应用的上传和下载逻辑。B 的业务实现独立于文件存储。

- `pyproject.toml` 和 `uv.lock` 统一声明并锁定 Pillow。成员运行 `uv sync --frozen` 安装依赖。
- Django 本地文件存储使用 `MEDIA_ROOT = BASE_DIR / "var" / "uploads"`。物品图使用 `items/` 子路径，争议附件使用 `disputes/` 子路径。项目在首次写入时创建所需目录，运行账号需要有写入权限。仓库根 `.gitignore` 排除 `campus-market/var/uploads/`。
- 上传目录独立于静态资源。应用通过各自的 Django 视图按对象状态和角色提供文件。根路由在任何 `DEBUG` 模式下均不挂载整个上传目录，Web 服务器也不直接映射该目录。
- 图片校验使用 Pillow 实际读取并限制解码尺寸。存储键由服务端生成，采用独立且不可复用的名称，原文件名只作展示。测试用临时存储目录，提交中只放少量明确为测试用途的素材，或者在测试里动态生成。

以下的文件数量、大小、格式和 B 的重新确认规则是本轮拟采用的开发口径。项目负责人发布任务时一并确认，有调整时先更新此文和开工约定。

## 2. 架构约束

三个模块都接入同一个 Django 单体，使用同一套 URL、会话认证、模板和 SQLite 数据库。每项功能在现有应用内完成，本轮沿用现有服务调用和同步事务，维持单个 `manage.py` 启动入口。

| 层次 | 职责 |
| --- | --- |
| `urls.py`、`views.py` | 在所属应用注册有命名空间的路由。视图读取当前会话用户，加载请求对象，绑定表单，调用服务并返回页面、重定向或文件响应。 |
| `forms.py`、`templates/<app>/` | 表单解析输入、校验字段及上传内容；模板继承现有页面骨架，按角色展示可用操作。写请求使用 POST 和 CSRF，服务端独立校验对象权限与当前状态。 |
| `services.py` | 执行业务状态转换、处理权限与幂等、协调跨应用调用。多条数据库写入属于一次业务操作时使用事务；唯一认领、重复确认和限额等并发约束须能在 SQLite 上验证。 |
| `models.py`、`migrations/` | 维护所属应用的数据、关系和约束。各模块提交本应用的增量迁移，并兼容基线已有记录。 |

### 数据归属与跨模块接口

| 模块 | 主责数据 | 本轮可复用的现有边界 |
| --- | --- | --- |
| A `catalog` | 物品、图片及公开资格 | 通过 `accounts.services.is_verified` 查询身份，通过 `transfers.services.active_transfer_for_item` 查询进行中流转；继续由 `catalog.services.can_display` 判定访客可见性。 |
| B `transfers` | 流转、撤销协商、接单和重新确认 | 继续由原撤销服务调用 `catalog.services.change_availability` 处理下架，并沿用借用收尾、争议查询及 `payments.services.request_refund`。资金状态和回执由 `payments` 持有。 |
| C `loans` | 借用争议及附件 | 沿用 `Dispute.can_view` 判断下载权限，在本应用服务中校验上传角色和争议状态。附件操作独立于争议关闭、归还确认及退款。 |

- 跨应用读写优先调用现有服务；业务状态由所属应用修改。保持现有接口签名和返回语义，确需调整时在 PR 中列出调用方和兼容方案。模型外键可用字符串引用，新增迁移依赖以真实外键或数据迁移需要为准。A、B、C 的功能分支应能各自在共同基线上运行测试。
- A 与 C 共用底层文件存储和锁定依赖，各自定义文件用途、授权和路由。A 的公开判定以当前物品状态为准；C 的附件下载每次按争议对象授权。文件响应不经过整个上传目录的公开映射。
- `config/`、根路由、公共模板、`pyproject.toml`、`uv.lock` 和全局存储设置由集成者统一维护。模块页面、路由和测试放在各自应用中；只有验证跨包行为的用例进入根目录 `tests/`。

## 3. 模块 A 物品图片上传、审核与展示

**目标**　物主可给物品添加一张可选图片。图片随物品审核，审核通过的公开物品在市场列表和详情显示图片。对应 CP-R-08、CP-D-03/05/10。沿用 `Item`、`ItemForm`、`create_item`、`edit_item`、`review_item`、`can_display` 和 `items` 路由。

### 功能与权限

1. 发布页支持上传；编辑页支持保留、替换和明确移除。使用 Django 表单和 `multipart/form-data`，绑定 `request.FILES`。编辑时未选择文件表示保留原图。已有物品和无图物品正常运行，列表和详情使用现有页面占位方式。
2. 单图支持 JPEG、PNG。源文件及最终存储文件均不超过 5 MiB，宽高各不超过 4096 像素。服务端先检查大小与格式，再验证能否解码。图片以合法格式重新编码并去除原图的 EXIF 等元数据；错误显示在对应表单字段。
3. 物主和具有现有物品审核权限的管理员可预览待审图片。访客和无关用户只有在 `can_display` 为真时能通过列表、详情或图片地址取得图片。当前预留的接收方可在有权访问该物品详情时查看已通过审核的当前图片。图片路由在每次请求时重新检查权限，缓存策略也须支持下架或转待审后撤销访问。
4. 添加、更换、移除图片均走现有物品编辑及重审流程。进行中的预留或借用按原规则禁止编辑。待审、驳回或下架时，访客用先前的图片地址也无法访问。替换后原地址失效；图片 URL 使用文件版本或等效标识，旧链接不得误指向新图。
5. 保存失败时已有图片仍可正常使用，且不会留下可访问的半完成记录。旧文件在数据库变更成功后才可清理；同一存储键不得被多个物品共享。历史版本留存为后续任务。

### 验收用例

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| A1 | 用虚构已认证账号发布无图物品与带图物品 | 都能提交审核，待审图对访客不可访问，管理员能预览 |
| A2 | 通过审核，再更换图片 | 原图审核通过后可在市场展示；更换后新图待审，访客使用新旧地址都无法取图；再次审核通过后展示新图 |
| A3 | 不选择文件编辑，再主动移除图片 | 两次操作分别保留和移除图片，均按现有规则重审 |
| A4 | 上传超限、损坏或仅改后缀的图片，或从非物主账号直接提交编辑 | 请求被拒绝，已有图片与记录保持一致 |
| A5 | 预留期间尝试换图；下架后访问旧图地址 | 换图被拒绝；旧图对访客不可访问 |

涉及模型变更时提交 `catalog` 迁移。重点检查 `apps/catalog/tests_views.py`、`apps/catalog/tests.py`，执行 `uv run python manage.py test apps.catalog`。

## 4. 模块 B 撤销去向分歧的管理员接单与双确认

**目标**　把现有的「双方去向声明不一致」日志接到管理员工作入口。双方仍各自确认物品去向，撤销生效与模拟退款沿用现有规则。对应 CP-R-12/13/25、CP-BR-09/10、CP-D-13、CP-ST-16/17/34。

### 状态与权限

| 阶段 | 操作与进入条件 | 持久化结果 |
| --- | --- | --- |
| 待认领 | 一笔有效撤销协商中，双方同意撤销，且分别选择了不同去向 | 同一协商可定位到一条处理记录，保存原声明及时间。流转继续处于撤销协商中 |
| 管理员核对 | 有效 `is_staff` 账号从「流转记录」进入待处理列表并认领 | 保存负责人及认领时间。并发认领只有一人成功，其他管理员无法代为处理 |
| 等待重新确认 | 负责管理员填写处理说明，发起一轮重新确认 | 保存说明、操作者、时间和本轮标识。原始声明及之前的轮次可追溯 |
| 双方确认一致 | 物主和获选接收方分别在同一轮选择 `未交出` 或 `已退回`，且双方仍同意撤销 | 调用现有撤销生效逻辑。保留物品下架、借用约定收尾、满足条件时模拟退款等行为 |
| 双方仍有分歧 | 同一轮两份声明不同 | 记录本轮结果，回到负责管理员处理。管理员可补充说明并开启新一轮 |
| 双方撤回 | 沿用现有双方撤回协商的入口 | 关闭本次处理入口，恢复现有规则允许的原流程，保留历史。迟到的旧轮次请求被拒绝 |

### 实现边界

- 页面接入 `apps/transfers/` 已有的管理员流转记录与当事人流转详情。处理说明可由当事双方及负责管理员查看。未认领的列表只展示接单所需摘要。写操作同时校验角色、协商主键、轮次和当前状态。
- 管理员可接单、登记说明和发起重新确认。去向声明只能由相应当事人提交本人结果。使用独立的轮次标识校验旧页面提交，双方确认必须属于同一轮。分歧处理期间，原去向提交入口也须校验当前阶段，避免旧表单绕过重新确认。任一方撤回时暂停当前轮次的确认，按既有规则等待另一方撤回。重复请求不重复认领、开轮或触发模拟退款，不同内容的重复提交不得覆盖已确认结果。
- 复用 `Revocation.Direction`、`Transfer.revoke_status` 和现有撤销收尾入口。不要用新状态覆盖 `Transfer.status` 或资金状态。协商期间继续由原有服务暂停交付及资金推进，已发出的模拟资金操作仍按现有回执规则记录。退款由原服务判断是否符合条件及是否已存在。
- 给迁移前已存在、仍在协商且双方去向冲突的记录提供接单入口，可用可重复识别的条件兼容旧记录。已撤回、已撤销以及不存在冲突的历史协商不进入待办。

### 验收用例

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| B1 | 有一方已确认交付，双方都同意撤销但去向不同 | 待办出现一次，仍处于撤销协商，未发起模拟退款 |
| B2 | 两名管理员尝试认领同一笔；普通用户直接 POST 接单或处理地址 | 只有一个负责人，越权操作失败 |
| B3 | 管理员开轮，一方先确认，另一方随后确认相同结果 | 单方提交不足以撤销；双确认后完成撤销，已付款且符合条件时最多生成一条模拟退款 |
| B4 | 首轮仍不一致，开启下一轮后提交旧页面表单 | 旧轮次提交被拒绝，双方本轮确认按当前轮次判断 |
| B5 | 已接单后双方撤回，之后再打开旧确认链接 | 原流程按既有规则恢复，历史可查，旧处理入口不可继续操作 |
| B6 | 旧数据升级、无分歧协商及重复确认 | 历史待处理记录可接单，无分歧的原流程继续可用，重复操作不新增退款或改写记录 |

涉及模型变更时提交 `transfers` 迁移。重点验证 `apps/transfers/services.py` 的 `_maybe_complete_revoke`、`declare_direction`、`withdraw_revoke` 和相关网页路由。执行 `uv run python manage.py test apps.transfers apps.payments`。

## 5. 模块 C 借用争议附件上传与受控下载

**目标**　借用损坏或丢失争议的双方能补充图片证据，负责管理员认领后可以查看。对应 CP-R-26、CP-D-14/15/22。沿用 `Dispute`、现有材料说明、负责管理员和 `Dispute.can_view` 的对象权限。

### 功能与权限

1. 在已创建的争议详情提供独立的上传表单。争议处理中，两位当事人均可补充，单次上传一份，每个争议最多五份。争议关闭后保留历史与原有授权下载。新附件作为追加材料，原条目可追溯。
2. 首轮接受 JPEG、PNG，每份不超过 5 MiB，宽高各不超过 4096 像素。校验真实图片格式、尺寸和可解码性。保留经验证的文件内容作为证据，用安全的显示文件名提供下载。保存争议关联、上传者、上传时间、文件名、大小和内部存储键。
3. 两位当事人和负责管理员可查看附件列表及下载。未认领时两位当事人仍可访问；普通第三方、未认领的管理员及无分配关系的超级管理员也应被拒绝。下载用同一个授权视图校验附件确属当前争议，返回文件下载响应，并设置私有缓存策略。模板使用应用路由生成链接。
4. 现有数据控制台可以查询争议摘要及文字记录。本轮新增附件只经受控入口访问，数据控制台不注册附件模型、不提供文件链接、原始存储键或路径。保留原有争议处理和归还、赔偿、押金状态转换。
5. 校验失败、超额或争议已关闭时，返回具体错误，且不留下附件记录或残留的新文件。并发上传同一争议时仍须遵守总数上限。下载时遇到文件缺失返回可理解的失败响应，避免暴露机器路径。

### 验收用例

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| C1 | 物主和借用者各上传一张合法图片，负责管理员认领 | 两位当事人可见，认领后负责人也可下载，记录上传人和时间 |
| C2 | 第三方、未认领管理员和其他超级管理员分别直接访问附件地址 | 均无法取得文件内容，替换 URL 中争议或附件编号也无法绕过授权 |
| C3 | 上传损坏、伪装或超限文件，或上传第六份附件 | 表单报错，已成功上传的证据不受影响 |
| C4 | 关闭争议后尝试上传并下载已有附件 | 上传被拒绝，已授权角色仍可下载历史附件 |
| C5 | 从旧数据库迁移、在临时目录执行测试 | 原有争议文字和关闭记录保留，测试文件不会写入真实上传目录 |

涉及模型变更时提交 `loans` 迁移。重点检查 `apps/loans/models.py`、`views.py`、`forms.py` 及争议相关模板。执行 `uv run python manage.py test apps.loans`。

## 6. 分支交付及合并门槛

### 分支负责人交付前

1. 每人提交一个功能分支和一个目标为 `main` 的 PR。提交标题写清改动，保证应用代码、模板、测试和对应迁移在同一分支内。共用配置、依赖、根 URL、公共模板与其他应用的必要修改先在 PR 中单列，由集成者协调。应用的新 URL 优先加到本应用现有 `urls.py`。
2. 只生成本应用的必要迁移，保持已发布迁移可用。用空数据库验证从零迁移，用基线测试数据验证升级后旧记录可用。交接时写明迁移文件和执行顺序；使用脚本或文档中的虚构步骤重建演示数据。
3. 在本分支运行以下检查，再运行模块专属测试。Python 格式检查范围为本 PR 变更的 Python 文件，可使用 `uv run ruff format --check <文件路径>`。手工演示至少包含一个成功场景和一个拒绝场景，PR 记录实测结果和未验证项。

```powershell
uv sync --frozen
uv run python manage.py migrate
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run ruff check apps config tests manage.py
git diff --check
git status --short --branch
```

4. 检查已跟踪文件中只有该模块的交付内容。`.venv`、SQLite 数据库、真实上传文件、密钥、缓存、日志及临时演示截图留在本地。提交后运行 `git diff --check "$base...HEAD"`，核对 `git log --oneline "$base..HEAD"`，并推送。

```powershell
git push -u origin $branch
git rev-parse HEAD
```

### PR 说明模板

```text
模块和负责人
分支、目标分支、开工基线 SHA、交付 SHA
范围和实现入口（主要文件、路由名称、操作角色）
共用文件或接口改动（无则写无）
迁移文件及顺序、已有数据如何兼容、运行目录或配置要求
需求编号和验收编号 → 测试模块／手工操作 → 实际结果
从空库启动与从旧库升级的结果，实测 OS、Python、uv 版本
剩余问题和未验证项
```

### 集成者验收顺序

1. 先检查共用上传提交，再看三条 PR 的开工 SHA、应用边界和迁移依赖。三包无新增依赖关系时，建议按 A → C → B 集成。每合入一项跑对应模块测试，遇到冲突由修改该模块的一方协助定位。
2. 在集成分支运行 `uv sync --frozen`、`uv run python manage.py migrate`、`uv run python manage.py check`、`uv run python manage.py makemigrations --check --dry-run` 和 `uv run python manage.py test`。再用一份基线虚构数据验证迁移升级。
3. 联调时重点复验三条边界。物品图转待审后访客旧链接失效，争议附件在 `DEBUG=False` 下仍受对象授权，撤销只有同轮双确认且规则满足时才可能触发模拟退款。最后复验买卖、赠送、借还和模拟资金人工办结的原入口。
