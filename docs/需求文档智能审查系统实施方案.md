# 软件项目需求文档智能审查系统：实施与验收方案

日期：2026-10-14。状态：当前选题方案，供团队评估；尚未开始业务实现。

## 1. 当前目标与资源

用户已经明确更希望实现本项目，教师鼓励使用人工智能，目标是尽可能提高交付完成程度。因此本方案以完整的智能审查产品为目标，不再按交易平台实施。

已知条件：四位成员，均已接入 GitHub，各有 AI 助手；本助手承担主要工程。用户回答投入“最多 20 小时”，本文按每人每周上限 20 小时理解，暂沿用四周；如果实际含义或周期不同，应同步修订预算。

团队投入上限为 4 × 4 × 20 = 320 人时。计划核心实现 240 人时、风险缓冲 40 人时、增强功能最多 40 人时。核心加缓冲合计 280 人时，平均每人每周 17.5 小时；不会在核心未通过验收时提前用完增强预算。

已有工程为 Python 3.13、Django 5.2、uv、Ruff，业务尚未实现。优先沿用该工程，把时间投入审查能力和完成质量。

## 2. 产品定位与完成程度

面向软件工程课程小组与小型项目团队，帮助作者和审查人发现、定位、核实及修复需求文档中的质量问题。

目标闭环：**上传需求 → 确认解析 → 规则及 AI 审查 → 查看原文证据 → 人工复核 → 修订新版本 → 复审 → 导出结论与过程报告。**

完成程度优先按这个顺序衡量：业务闭环完整、结果有依据、异常可处理、效果有证据、环境可复现，然后才是更多模型、更多格式和更复杂界面。

用户角色：文档作者负责上传和修订；审查人员确认问题；项目负责人管理成员、清单及审查进度；管理员管理服务配置和异常。一个用户可以兼任多个角色，但每次操作记录实际操作者。

### 2.1 三档交付目标

| 档位 | 完成定义 | 本期安排 |
| --- | --- | --- |
| 验证原型 | 一个文本输入、真实模型调用和可定位问题 | 第 1 周早期验证工程路径，不作为最终交付 |
| 完整核心版 | 权限、文档版本、解析、混合审查、复核、修订复审、报告、测试和运行说明形成闭环 | 240 人时核心目标 |
| 增强版 | 在核心通过验收后，强化跨版本追踪、测试建议与效果展示 | 使用最多 40 人时增强预算，按收益顺序实施 |

## 3. 审查能力如何落地

采用“确定性规则 + AI 辅助判断 + 人工复核”。规则提供稳定检查，AI 处理语义问题，人处理业务结论；不把模型输出直接等同于已确认缺陷。

| 审查维度 | 输入或依据 | 输出与边界 |
| --- | --- | --- |
| 结构完整性 | 项目选定的需求模板 | 缺少已要求的章节；不据此宣称所有业务需求齐全 |
| 表述明确性 | 原文、角色、条件、术语 | 定位“尽快”“友好”等含糊表述，并解释缺少什么条件 |
| 可测试性 | 功能和质量需求 | 检查是否缺少触发条件、边界或可观察结果；示例阈值标为建议 |
| 术语一致性 | 原文提取及人工确认的术语表 | 标记疑似同义异名、同名异义；保留相应证据 |
| 条目冲突 | 相关条目、数值、权限、约束 | 给出冲突双方位置与推理；结论仍待复核 |
| 重复与歧义 | 同文档条目及上下文 | 区分疑似重复和真正冲突，避免合并掉不同场景 |
| 角色与异常流程 | 项目角色、主要流程及需求条目 | 提出缺少权限、失败或取消路径的待核实问题 |
| 需求可追溯性 | 用户提供的来源、需求 ID 与引用 | 检查缺失或失效引用；没有来源时标记待补充 |

业务可行性、法规适用和未提供的业务规则只输出“需领域人员确认”，不自动给出通过结论。系统不给无依据的文档总分，先展示问题分布、审查范围、待确认项和人工结论。

### 3.1 每条问题必须包含的内容

问题 ID、所属文档版本、问题类别、建议严重程度、规则或 AI 来源、原文块 ID、原文片段、理由、建议及人工处理状态。冲突问题至少关联两个原文位置；章节缺失问题引用模板检查项与对应章节范围，不能虚构不存在的原文。

改写中新增的数值、超时、角色或业务约束必须标为待确认建议。未获得用户认可的建议不能自动写回原文。

## 4. 核心需求与验收对应

以下均是当前方案的建议需求，不是已经实现或通过的结果。R 表示需求，T 表示计划测试。

| 编号 | 核心需求 | 验收条件 | 测试 |
| --- | --- | --- | --- |
| R-01 | 账号、项目与成员角色 | 非成员不能读文档、结果或下载报告；审查操作按角色控制 | T-01 |
| R-02 | 文档上传与不可变版本 | 上传生成独立版本，文件和解析结果对应；旧版不被覆盖 | T-02 |
| R-03 | 解析、结构和原文定位 | 支持 TXT、Markdown、DOCX、文本型 PDF；内容可预览，问题可跳到原文 | T-03 |
| R-04 | 模板、术语与规则检查 | 使用选定清单检查，显示规则依据与版本；同样输入可复现规则结果 | T-04 |
| R-05 | 真实模型辅助审查 | 按选定维度生成结构化问题；服务端核对类型、字段、原文位置和引用 | T-05 |
| R-06 | 审查任务与失败处理 | 待执行、执行中、成功、部分失败、失败可区分；可安全重试，不把失败当通过 | T-06 |
| R-07 | 审查工作台与人工复核 | 原文与问题并列；支持筛选、确认、驳回、备注，保留操作历史 | T-07 |
| R-08 | 新版本复审与问题关联 | 可上传修订版并重审；允许关联旧问题，机器疑似解决需人确认 | T-08 |
| R-09 | 报告与概览 | 导出 HTML、CSV；包含文档版本、范围、问题、人工结论、执行版本和失败说明 | T-09 |
| R-10 | 运行配置与可观测信息 | 服务端配置模型；记录任务耗时、调用用量（若接口提供）和异常，不泄露密钥 | T-10 |
| R-11 | 效果评价 | 固定样本和匹配规则，对比规则、AI、混合三种方式；保存可复查结果 | T-11 |

### 4.1 格式与质量边界

TXT、Markdown 按行与段落定位；DOCX 按标题、段落和表格单元格定位，不承诺还原 Word 页码；PDF 按页与提取文本块定位，并提示复杂多栏或表格可能存在读取顺序问题。

建议初始限制为单文件 10 MB、提取文本不超过 4 万字符，具体限制在格式验证和模型耗时试验后冻结。不能因分块而静默漏掉超出范围的内容，报告必须说明实际覆盖范围。

扫描件 PDF 与 OCR、多模态图表理解、旧版 DOC 文件、复杂修订痕迹不纳入核心格式承诺。上传后遇到无可提取文本、加密文件或解析异常时给出具体原因和处理办法。

## 5. 完整业务流程

### 5.1 从初审到复审

1. 负责人建立项目，添加成员，选定需求模板和审查维度，补充已知角色、业务背景与术语。
2. 作者上传文档，系统生成版本、校验文件并解析；作者核对预览内容和解析提示。
3. 作者发起审查，系统固定文档版本、规则版本、提示模板及模型信息，创建持久化任务。
4. 任务执行规则检查，按标题和条目拆分文本；模型先审局部，再对提取出的条目、术语和约束进行全局关系检查。
5. 服务端验证输出格式、原文 ID 与引用；无效结果标为异常，不混入已验证位置的问题。
6. 去重并合并展示，保留规则与模型来源；部分块失败则标记覆盖缺口，允许重试失败部分。
7. 审查人员在工作台核实问题，确认或驳回，补充意见；作者查看已确认问题。
8. 作者在原有编辑工具中修改文档并上传新版本；系统保留旧版，重新审查新版本。
9. 审查人员关联新旧问题并确认解决情况；“新一轮没有报告”只能作为疑似解决提示，不能自动证明修复。
10. 导出报告，包含版本、覆盖范围、机器建议、人工结论和遗留问题；负责人记录本轮是否完成。

### 5.2 示例

原文：“系统应快速返回搜索结果。”

系统定位原文后，提出“性能条件不可验证”：缺少数据规模、并发规模和响应时间口径。建议改写应使用待填条件，例如“在【数据规模】和【并发量】条件下，【比例】的请求在【时间】内返回”。

若模型提出“95% 请求 2 秒内返回”，界面应标明这是建议值，需团队确认和实测，不能说成老师或用户已提出的要求。

### 5.3 异常与处理

| 异常 | 系统行为 |
| --- | --- |
| 文件无法解析或内容为空 | 不发起模型调用；保留明确错误和重传入口 |
| 模型超时、限流或凭据不可用 | 记录失败；限制自动重试次数；用户可重试；有效的规则结果单独展示 |
| 只有部分文档处理成功 | 标记部分失败，列出未覆盖块；不能显示全文审查完成 |
| 模型引用不存在的段落 | 拒收该条定位结果或标为需复核异常，不伪造证据 |
| 任务执行中上传新版本 | 原任务仍对应旧版，另建新任务，不混合两个版本 |
| 重复点击或工作进程中断 | 不重复发布同一次执行结果；中断任务可恢复或明确转失败 |
| 文档内含“忽略规则”等指令 | 当作待审内容；不给审查模型执行命令、修改文件或外发数据的工具权限 |
| 成员权限被撤销 | 立即失去文档与报告访问权限；保留必要历史记录 |

## 6. 页面、数据与工程路线

### 6.1 页面

登录；项目列表与成员管理；文档列表及上传；解析预览；审查配置和进度；原文与问题工作台；人工复核；版本复审；报告概览与导出；管理员配置与任务异常。

主界面优先解决三个问题：问题在哪里、依据是什么、下一步如何处理。跨版本对比可先用列表和原文片段，不把在线文档编辑器列入核心范围。

### 6.2 数据

| 对象 | 关键内容 |
| --- | --- |
| Project／Membership | 项目、成员、角色、业务背景 |
| Document／DocumentVersion | 文档、不可变版本、文件、内容摘要与解析状态 |
| TextBlock／RequirementItem | 原文位置、层级、条目 ID；原文与 AI 提取内容分别保存 |
| ReviewProfile | 模板、清单、术语与规则版本 |
| ReviewRun | 文档版本、执行状态、覆盖块、模型与提示版本、耗时、失败信息 |
| Finding | 问题、类别、严重程度建议、来源、引用、理由和改写建议 |
| ReviewDecision | 人工确认或驳回、备注、操作者与时间 |
| FindingLink | 跨版本候选关联、人工确认的解决或延续关系 |
| EvaluationCase／Result | 固定样本、标注、匹配规则与评价结果 |

报告由这些版本化记录生成。人工结论与机器输出分开保存，重跑审查不能覆盖已经作出的人工判断。

### 6.3 实现选择

采用现有 Django 单体工程，模板页面配合必要的交互脚本；按项目权限、文档、审查与报告等业务组织代码。先核对标准库与现有依赖，仅增加解析 DOCX、PDF 和实际模型接入所需的依赖。

审查采用持久化任务记录与独立工作进程，页面查询进度，避免一次长 HTTP 请求承担全文审查。初版先验证单工作进程的超时、中断及重试；只有实测显示必要时才增加队列基础设施。

先接通一个真实模型服务，不同时实现多家厂商切换。四个人的开发助手不自动成为应用的运行服务；第 2 天前须验证模型调用方式、账户权限、数据去向、实际耗时和用量。密钥通过服务端环境配置，不粘贴到文档或提交 GitHub。

全文解析与页面先用 SQLite 开发；独立工作进程和多人操作下的任务领取、写入与状态一致性需要实测。若出现锁冲突或确定多人部署，第一周安排 PostgreSQL，避免临近交付才换数据库。

初版按文档结构分块与条目关系检查；不默认引入向量数据库、RAG、微调和多智能体架构。若后续需要审查项目规范库，先证明基线检索不足，再单独增加相关能力。

## 7. 效果验证与交付质量

### 7.1 可核实的评价方法

建议准备 20 份短文档，覆盖不同模板、无明显缺陷文档和含多类缺陷文档，至少 100 个标注问题。每份由两名成员独立审查，分歧由项目负责人汇总，争议项请教师或有审查经验的人确认；成员标注不能直接称为专家金标准。

按文档划分 12 份调试集与 8 份独立验收集，不把同一文档的近似修订版分放两组。保存样本哈希、人工标注版本和问题匹配规则；验收集不用于反复调整提示词。

评价问题匹配需同时考虑类别、原文范围和缺陷含义；重复报告只算一次命中；一对一匹配后计算查准率、查全率与 F1。对确有分歧的判断单独展示，避免只挑选有利案例。

| 对照组 | 目的 |
| --- | --- |
| 仅规则 | 确定稳定检查能覆盖哪些问题 |
| 仅 AI | 观察语义检查的增益与误报 |
| 规则 + AI | 检查混合方式的总体表现与问题互补 |

记录各类别指标和样本数量、原文定位有效率、人工采纳率、任务成功率、耗时分布及模型用量。对同一小组样本重复运行至少三次，观察结果稳定性；这部分样本与独立验收报告分开说明。

模型生成错误内容是需要测量的质量问题；NIST 相关文件可作为评价设计背景，而非给本项目提供现成通过阈值。[NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

### 7.2 目标与完成门槛

建议调优目标：在确定的验收样本上，语义问题查准率达到 80%、查全率达到 70%；这是拟定目标，不是已实现结果，也不代表所有领域效果。第 1 周试验后判断是否合理，若修改目标，应在冻结验收集前记录理由。

确定性门槛：已发布的问题引用指向真实原文或明确模板项；权限检查通过；失败与部分覆盖明确显示；旧版不被覆盖；任务可恢复或明确失败；导出与工作台一致；无未解决的越权、数据丢失或主流程阻断缺陷。

模型未达到拟定目标时，提交实测结果、误报漏报分析和适用范围，不改造验收样本来掩盖结果。完整交付包括清楚呈现不足。

提示注入防护需要系统权限边界和验证，不能只加一句提示词。核心审查模型不获得外部操作工具，上传内容与控制指令分离，并加入恶意文档测试。[OWASP 提示注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

## 9. 四人与 AI 助手协作

| 责任 | 主要工作 | 本助手配合 |
| --- | --- | --- |
| 成员 A：需求与集成协调 | 确认模板和规则、老师沟通、需求基线、周验收 | 细化设计，统一业务规则和核心实现 |
| 成员 B：解析与使用体验 | 格式样本、解析核对、工作台页面验收 | 主要实现解析与页面流程，修复定位问题 |
| 成员 C：质量与效果 | 双人标注组织、异常测试、评价结果复核 | 建立测试和评价脚本，处理失败与误报漏报 |
| 成员 D：交付与文档 | 版本复审体验、报告核对、环境复现与答辩 | 实现复审、报告和运行配置，完成集成 |

本助手负责主要架构、模型、权限、审查流程、核心页面、测试工具及集成。其他助手可以处理明确范围的页面、样本、独立测试和文档；每位成员对最终交付负责复核，并能解释自己的工作。

GitHub 任务建议按 R-01 至 R-12 拆分，注明依赖、范围、验收案例、负责人和测试证据。公共模型、数据库迁移和审查结果协议统一整合；短分支、小 PR，至少一名其他成员复核后集成，重跑关键测试。

协作依靠共享任务、文档和 PR，不假设各助手已经自动互通。当前尚未创建远程任务或启动后台持续执行。

## 10. 增强顺序与取舍

核心版通过后按以下顺序投入，做到哪里就以实际验收为准：

1. **跨版本问题追踪增强：**提示新增、持续和疑似解决问题，人工确认；提升闭环完成程度。
2. **验收条件与测试建议：**为已确认问题生成可编辑的用户故事、验收条件及测试草案，关联原需求，不自动当成事实。
3. **评价与趋势展示：**展示人工确认问题分布、版本变化、审查耗时和对照实验，明确统计口径。
4. **PDF 报告：**在 HTML／CSV 已通过验收后增加，验证中文字体、分页及原文引用。

OCR、大型项目规范知识库、多模型对比平台、在线协同编辑和模型微调另立范围，不为增加功能数量牺牲已承诺能力。
