## 1. 结论与评估依据

**历史评估结论：在较低投入、偏重可预测交付的前提下，原先推荐校园交易平台。用户现已选择智能审查系统，后续按新的目标与投入重新安排。**

选择理由是：在四周内，交易平台更容易形成可演示、可测试、可解释的业务闭环；智能审查系统除了常规软件开发，还需要审查标准、专业标注样本、模型接入和效果评价。这些工作无法仅靠增加 AI 助手数量消除。

## 2. 两个项目的需求评估

### 2.1 软件项目需求文档智能审查系统

#### 领域背景与问题

面向软件工程课程小组或小型开发团队，辅助发现需求文档中表达含糊、验收条件缺失、术语不一致、模板章节缺失和潜在冲突。目标是减少人工查找与整理问题的时间，最终结论由审查人员确认。

“系统给出建议”与“系统判断业务正确”必须区分。缺少领域背景时，模型不能可靠证明需求完整、可行或符合真实业务。

#### 角色

| 角色 | 主要职责 |
| --- | --- |
| 文档作者 | 建立项目、上传版本、查看问题、修改需求 |
| 审查人员 | 确认或驳回建议、调整严重程度、检查修订结果 |
| 项目负责人 | 维护项目成员、审查清单、版本和审查进度 |
| 管理员 | 管理账号、访问权限、模型配置与任务异常 |

同一用户可以同时担任作者与负责人，但应分别记录机器建议与人工处理结果。

#### 建议首版需求

| 编号 | 功能 | 可验证结果 |
| --- | --- | --- |
| AI-01 | 项目、成员与文档权限 | 非项目成员不能读取文档和审查结果 |
| AI-02 | 文档版本与解析 | 首版支持 TXT、DOCX；解析后展示段落编号；不支持的格式明确拒绝 |
| AI-03 | 固定审查清单 | 对指定模板检查章节、模糊表达、可测量验收条件；规则与解释可查看 |
| AI-04 | 模型辅助审查 | 每条建议含问题类别、原文位置、依据、修改建议和人工复核状态 |
| AI-05 | 审查任务状态 | 待执行、执行中、成功、失败可区分；失败不能展示为“没有问题” |
| AI-06 | 人工复核与修订 | 可接受、驳回、备注；新版本重审保留旧版本结果 |
| AI-07 | 报告与过程记录 | 导出问题及人工结论；保留模型、规则、提示模板版本与执行时间 |

文本型 PDF 可作为扩展；扫描件 OCR、多人实时编辑、模型训练、任意专业领域自动审查不进入四周首版。固定审查清单不等于要开发通用规则编辑器。

#### 核心流程

建立项目与权限 → 上传文档版本 → 解析并核对原文 → 按清单执行规则检查与模型审查 → 校验结果格式及原文引用 → 人工复核 → 修改并上传新版本 → 复审 → 导出报告。

模型输出格式错误、引用段落不存在或接口超时，应进入失败或需复核状态，不能自动给出“通过”。上传文档中的指令只能作为待审文本处理，不得覆盖系统审查规则。

#### 领域术语

| 术语 | 本项目中的含义 |
| --- | --- |
| 需求条目 | 可单独标识和讨论的一项功能、约束或质量要求 |
| 审查规则 | 具有明确适用范围和判定依据的检查项 |
| 完整性 | 针对约定模板和范围检查是否缺项，不能据此证明所有业务需求齐全 |
| 一致性 | 对术语、数值、角色权限和条目关系进行冲突检查 |
| 可测试性 | 是否提供足以设计验收测试的条件与预期结果 |
| 误报／漏报 | 报告了人工认定不存在的问题／遗漏人工认定存在的问题 |
| 审查基线 | 冻结的文档、规则及评价样本版本 |

#### 非功能需求与效果验收

- 文档和报告按项目授权访问；保留版本与审查依据；密钥仅在服务端保存。
- 调用外部模型前明确数据去向；课程演示优先使用无敏感信息的自建样本。
- 模型失败时保留任务记录和文档，允许用户重试；规则检查可以独立展示，但须说明覆盖范围。
- 建议由教师或有需求审查经验的人确认 10—20 份短文档样本，合计约 80—150 个标注检查点，包含正确条目与故意植入的问题。数量是建议，不能代替实际标注质量。
- 样本分成调试集和独立验收集，避免边调提示词边用同一组样本宣称效果。
- 分类别统计查准率 precision（正确报告问题数／报告问题总数）和查全率 recall（检出问题数／人工标注问题总数）、原文引用有效率、人工采纳率、耗时及调用成本。报告分母和标注分歧；没有有效分母时注明不适用。
- 具体通过阈值应由老师或领域审查人员确认；没有确认前，不应承诺“准确率 95%”或“可以替代人工审查”。

#### 不确定问题清单

1. 审查对象是课程需求规格说明书，还是企业文档？是否有固定模板？
2. 必须支持哪些语言、格式和最大长度？是否包含表格或图片？
3. 是否允许向外部模型上传文档？是否有预算和稳定网络？
4. 项目按功能完成度验收，还是必须证明智能审查效果？
5. “跨版本问题已解决”是否需要自动匹配，还是人工确认即可？

#### 需要领域专家确认的问题

1. 各类问题的定义、严重程度及正反例是什么？
2. 哪些检查允许确定性判定，哪些只能输出待核实建议？
3. 样本标注由谁负责，标注意见冲突如何裁定？
4. 对漏报与误报的容忍程度，以及验收指标是什么？
5. 如何检查业务完整性、需求可行性和跨条目冲突，所需业务背景从哪里取得？

#### AI 生成需求与审查的风险

AI 可能生成看似合理却无来源的业务规则、虚构约束、混淆用户角色、过度承诺性能，或对同一需求多次给出不同判断。审查模型也可能漏报、误报、虚构原文引用，或受到文档中恶意指令的影响。

处理办法是给需求记录来源、假设和待确认项；给建议保留原文证据；固定验收样本与执行版本；由人确认最终结论。NIST 的生成式 AI 风险文件将自信输出错误内容列为风险，支持这里保留人工复核和独立评价的设计。[NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

#### 可行性结论

工程原型可实现，但专业效果具有较大不确定性。若目前没有审查标准、标注样本和专家支持，四周容易得到“上传文档后调用模型返回建议”的演示，难以证明审查质量。若团队更看重 AI 研究，且前两天能确认标准、样本与接口，则可以重新考虑此选题。

### 2.2 校园二手交易与物品流转平台

#### 业务背景与角色

为单个校园内的闲置物品提供统一发布、检索、沟通、预约交易、线下交付和反馈记录。需求调研应验证学生是否确实遇到信息分散、物品是否可买不清楚、重复约定交易以及交付后缺少记录的问题，不能直接当成已证实事实。

- 游客：浏览经过审核的可售物品。
- 学生用户：注册认证；同一账号可以出售和购买不同物品。
- 管理员：认证审核、商品审核、举报处理和账号限制。

卖家与买家是交易中的角色，不是两套互斥账号体系。平台记录双方确认，不保证线下支付或实物交接的真实性。

#### 与课程十类功能对应的首版范围

| 编号 | 课程功能 | 四周内建议完成的实现 | 验收例子 |
| --- | --- | --- | --- |
| TR-01 | 注册与认证 | 账号登录；提交校园标识，管理员审批；演示用虚构资料 | 未认证用户能浏览，不能发布或下单 |
| TR-02 | 发布与审核 | 标题、描述、分类、成色、价格、图片；审核后展示 | 驳回需理由；修改关键内容需重新审核 |
| TR-03 | 搜索与筛选 | 关键词、分类、价格范围、分页与时间排序 | 下架、未审核商品不出现在公开结果 |
| TR-04 | 收藏与咨询 | 收藏去重；商品对应的买卖双方私密留言 | 第三人无法查看咨询内容 |
| TR-05 | 下单与确认 | 单物品预约；卖家接受或拒绝；取消记录 | 同一物品最多有一个有效订单 |
| TR-06 | 线下交付 | 约定校内地点与时间；分别确认交出和收到 | 仅一方确认时订单不能完成 |
| TR-07 | 评价与举报 | 完成后双方各评价一次；对商品、用户或交易举报 | 未参与交易者不能评价该订单 |
| TR-08 | 审核与封禁 | 审核理由、举报处理结果、限制期限与操作日志 | 被限制用户不能新发布或新下单 |
| TR-09 | 状态流转 | 商品、订单状态按规则变化；保留事件记录 | 他人不能改卖家商品，已完成订单不能退回待交付 |
| TR-10 | 数据统计 | 发布量、已完成交易数、分类分布、完成订单约定金额汇总 | 数值可用明细核对；取消订单不计成交 |

“校园标识由管理员批准”是课程原型方案，不等于已经与学校完成身份验证。需老师确认其是否满足认证要求；不默认收集学生证照片，也不声称演示账号经过真实认证。

#### 首版边界

- 单校园、单件实物、一件物品对应一个独立商品条目；首版聚焦出售，不加入租赁、竞拍、交换和复杂赠送规则。
- 支付在线下自行完成；系统保存约定金额与双方确认，不接支付接口，不设钱包、押金或退款系统。
- 咨询采用普通私密留言和刷新查看；不要求实时聊天、语音或文件传输。
- 不接学校统一登录、物流、地图定位；交付地点填写校园公共地点名称。
- “物品流转”首版指发布到预约、交付、完成及取消的可追溯过程。跨持有人再次转卖的物品谱系属于扩展，需老师明确是否要求。
- 平台处理内容举报和账号限制；不承担资金托管或自动裁决线下责任。

这些边界保留课程列出的十类功能。若老师要求某项更深的实现，应明确替换优先级和验收条件，而非把新要求直接叠加到四周计划中。

#### 非功能需求建议

- 服务端检查登录、认证、对象归属和角色权限；页面隐藏按钮不能替代权限校验。
- 密码使用框架机制存储；上传图片检查类型和体积；输出转义并使用请求防伪保护。
- 咨询、认证资料和订单约定不公开；普通用户只能访问与自己相关的私密记录。
- 关键状态变更与操作原因可追溯；已经关联交易的商品采用隐藏／下架方式处理，保留历史证据。
- 关键操作重复提交不产生重复订单或重复评价；下单和商品预留在同一事务中完成。
- 建议验收环境预置 200 件商品、20 个测试账号；10 位用户同时进行浏览与筛选时，95% 请求在 2 秒内返回。指标须在固定机器和网络环境下实测；这不是已达到的结果或商业容量承诺。
- 正常空列表、无搜索结果、表单错误和无权限页面均能理解和操作，表单有标签并支持基本键盘访问。
- 准备数据库与图片备份，实际演练一次恢复；课程演示结束后清理测试个人资料。

#### 仍需确认的问题

认证方式及资料保留范围；禁售品类；商品审核标准；是否允许游客浏览；订单等待期限；取消和交付争议规则；“物品流转”是否包含再次转卖。首版流程以下文为建议基线，冻结前由成员通过调研和老师反馈确认。

#### 可行性结论

主要难点是状态和权限一致性，技术路径相对明确。可以以双重下单、越权、取消释放、双向交付确认为测试对象，形成直接可核对的证据。新意主要来自校内交付与全过程追溯，需要通过正确实现证明，不能仅靠页面数量体现。

## 3. 对比与最终推荐

下表是结合当前团队与四周期限的工程判断，不是客观实验评分或预期课程分数。

| 维度 | 智能审查系统 | 校园交易平台 |
| --- | --- | --- |
| 课程选题匹配 | 专业领域项目，需覆盖七项额外分析内容 | 熟悉业务项目，十类功能已明确 |
| 获取需求证据 | 需要懂需求审查的人和样本文档 | 可直接访谈学生和模拟交易 |
| 规则确定性 | 语义判断、完整性存在争议 | 权限、状态和交易条件可明确约定 |
| 核心验收 | 功能验收加审查效果评价 | 业务闭环、权限与状态测试 |
| 外部依赖 | 模型、网络、成本、数据权限 | 首版可在本地完整演示 |
| 现有工程适配 | 可复用 Django，但需增加解析与模型流程 | 可直接沿用现有工程 |
| 差异化潜力 | 较高，但需要效果证据支撑 | 中等，可突出追溯和异常流程 |
| 四周主要风险 | 功能完成但智能效果无法证明 | 功能扩张、状态并发错误和联调滞后 |
| 四周实现把握 | 在标准、样本未确定时较低 | 收紧范围后相对较高 |

**推荐方案：实验 2 做两套需求分析；实验 3 后选校园交易平台贯穿实施。**

若老师对 AI 创新有明确较高权重，且团队已有可用标注集、审查专家和模型接口，应重新权衡；目前没有这些证据，因此不以它们为前提排期。

## 4. 推荐项目的完整业务流程

### 4.1 一笔正常交易

1. 学生甲注册，提交校园标识，管理员批准认证。
2. 甲发布一本二手教材，填写成色、照片和价格。
3. 管理员审核通过，教材进入公开可售列表。
4. 学生乙搜索到教材，可收藏并向甲发送私密咨询。
5. 乙提交预约交易，系统检查认证、账号限制、卖家身份和物品状态；成功后创建待卖家确认订单，同时预留物品。
6. 甲接受预约；双方在订单页约定校内地点、时间和最终金额，分别确认同一约定版本。提出或修改约定后，旧的认可失效，必须重新确认。
7. 线下见面后，甲确认已交出，乙确认已收到。两次确认都到达后，订单才完成，商品进入已成交状态。
8. 双方可各评价一次；管理员统计反映已完成交易，历史页显示关键操作时间。

双方确认只是平台记录的证据，不代表系统能独立证明实物或款项已经交付。

### 4.2 商品与订单状态

商品状态与订单状态分开保存，商品保留每次关键变更的时间、操作者和原因。

| 对象 | 状态变化 | 发起条件 |
| --- | --- | --- |
| 商品 | 草稿 → 待审核 → 可售 | 所有人提交；管理员批准 |
| 商品 | 待审核 → 已驳回 → 待审核 | 管理员说明原因；所有人修改重提 |
| 商品 | 可售 → 已预留 | 创建有效订单成功 |
| 商品 | 已预留 → 已成交 | 对应订单完成 |
| 商品 | 已预留 → 可售 | 对应订单取消，且商品没有被下架、用户没有被限制 |
| 商品 | 可售 → 已下架 | 所有人主动下架或管理员处理违规 |
| 商品 | 已下架 → 待审核 | 所有人重提；管理员重新检查后才能恢复可售 |
| 订单 | 待卖家确认 → 待交付 | 卖家接受预约 |
| 订单 | 待卖家确认 → 已取消 | 买家取消、卖家拒绝，或符合约定超时规则 |
| 订单 | 待交付 → 已完成 | 双方均确认交付，且没有未处理的交付争议 |
| 订单 | 待交付 → 已取消 | 双方都尚未确认交付；允许任一方取消并记录原因 |

双方确认同一约定版本后才能提交交付确认；出现首个交付确认后，约定内容冻结。有一方确认交付后，不允许单方取消，需提交争议并由管理员记录处理结果。存在未处理的交付争议时暂停完成或取消操作；管理员可以按处理结果解除暂停，或在确认交易未完成后取消并写明依据，不能替代双方伪造交付确认。若两项确认已经存在，解除暂停后需由参与者再次发起完成请求并核对条件，不能永久停留在待交付状态。

首版默认采用买家主动取消、卖家拒绝及管理员按依据处理，不设置自动超时。这样减少定时任务依赖，但无人处理的预约会持续占用物品，需在“待处理订单”中清楚展示。若老师明确要求超时释放，再确认期限并同时增加定期处理、操作时期限校验和测试，不能仅显示倒计时。

### 4.3 必须写进设计与测试的业务规则

1. 一件物品同时只能有一个有效订单；不能只在页面上禁用下单按钮。
2. 卖家不能购买自己的物品；未认证、被限制用户不能发起新交易。
3. 创建订单必须与商品预留一起成功或一起回滚；并发冲突给出“物品已被预约”等可理解结果。
4. 有有效订单时，卖家不能修改价格、描述或撤销商品；先按订单规则处理，避免修改交易依据。
5. 订单保存标题、约定金额等必要快照；即使后来商品隐藏，参与者仍可查到历史。
6. 已完成订单不回退到可售；再次转卖需新发布，不修改原交易。
7. 重复确认不重复生成成交记录；每个参与者对一笔交易只能评价一次。
8. 商品咨询只有买卖双方及有处理需要的管理员可见；管理员访问应留痕。
9. 举报必须有明确对象、理由、处理人和结果，不能仅保存一段无关联文本。
10. 管理员下架正在交易的商品时，阻止新交易，保留现有订单并进入人工处理；取消后不得误恢复为可售。
11. 账号被限制时，禁止新发布和新下单；现有订单仍可查看、完成或申请处理，避免用户被挡在交付流程之外。
12. 约定金额汇总是双方记录的交易金额，不是平台收款额，也不能据此声称核实了实际支付。
13. 举报区分普通内容举报和关联有效订单的交付争议；普通举报不自动冻结交易。交易参与者或管理员可以提出交付争议并留痕，避免任意第三人通过举报阻断交易。
14. 因账号限制而未恢复可售的商品保持下架；解除账号限制后由所有人重提审核，不自动恢复交易。

### 4.4 异常流程

| 情况 | 处理流程与验收重点 |
| --- | --- |
| 商品审核未通过 | 展示原因 → 修改 → 重提；未经批准不公开 |
| 两人同时预约 | 原子预留，只允许一个有效订单；另一人看到失败原因 |
| 卖家拒绝／买家取消 | 订单保留取消原因；符合条件时释放物品 |
| 一方未确认交付 | 保持待交付；提醒或申请管理员处理，不自动完成 |
| 线下争议 | 提交关联订单的举报 → 暂停终态变更 → 管理员记录处理 → 双方继续确认或按依据取消 |
| 被举报或封禁 | 审核依据留痕；历史交易可追溯；限制不导致历史数据丢失 |
| 上传或提交失败 | 明确报错；不产生半条商品或半笔交易；可安全重试 |

## 5. 页面、数据和技术方案

### 5.1 页面范围

学生端包括登录注册与认证、商品列表和详情、发布编辑、我的商品、收藏、咨询、订单列表和详情、评价举报入口。管理员端复用 Django 管理后台，覆盖认证、商品、举报、用户限制与基础统计；只为后台无法清楚完成的流程补专门页面。

界面以清楚展示“当前状态、谁能执行下一步、为什么不能操作”为验收重点。手机浏览应能完成主流程，但不另做原生 App 或小程序。

### 5.2 核心数据

| 数据对象 | 关键内容 |
| --- | --- |
| 用户与校园资料 | 账号、校园标识、认证状态、限制状态及原因 |
| 分类与商品 | 发布人、标题、描述、价格、成色、审核及销售状态 |
| 商品图片 | 所属商品、文件、展示顺序 |
| 收藏 | 用户、商品，组合唯一 |
| 咨询消息 | 商品、发件人、收件人、内容、时间 |
| 订单 | 商品、双方、快照、约定版本与金额、状态、双方确认时间 |
| 评价 | 订单、评价人、被评价人、分数或文字，订单与评价人组合唯一 |
| 举报 | 对象、举报人、原因、处理状态、处理人及结果 |
| 状态与管理记录 | 业务对象、前后状态、操作者、理由和时间 |

流转记录随状态变更在同一事务内保存。统计由现有明细计算，首版无需另建统计数据平台。

### 5.3 实现路线

沿用仓库现有 Python、Django、uv 和 Ruff。前端先使用 Django 模板与少量 JavaScript；业务按用户、商品、交易、反馈等实际领域组织，避免为了分工同时搭建两套前后端工程。

SQLite 用于开始阶段的本地开发。下单使用数据库事务、带条件的状态更新和适当唯一约束维护一致性；发生锁冲突时，整个操作回滚并反馈，不能继续生成订单。

SQLite 上 `select_for_update()` 不提供有效的行锁，因此不能把调用该方法当作“已经解决并发”。若课程验收要求真实多人并发，或选定 PostgreSQL 作为部署数据库，应在第 1 周确认，并在该数据库上验证交易逻辑。[Django 5.2 官方文档](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update)

不默认引入微服务、消息队列、搜索集群、实时通信或容器编排。先完成一个可运行的业务闭环，再按证据增加必要组件。

## 6. 四周工程实施流程

### 6.1 分工与 AI 配合

本助手承担主要工程实现：架构细化、数据模型、核心交易逻辑、权限、关键测试和集成修复。四位成员共同决定需求和验收结论；其他助手的工作建议限定在有清晰输入输出的任务，避免同时改同一核心文件。

| 人员 | 主责 | 每周可检查的交付 |
| --- | --- | --- |
| 成员 A | 项目协调与需求核实；汇总问题并与主助手协作 | 需求基线、优先级、验收记录和进度 |
| 成员 B | 页面流程与使用体验验收 | 页面草图、表单提示检查、主流程人工验收 |
| 成员 C | 测试与质量复核 | 测试案例、异常场景复现、问题清单及回归结果 |
| 成员 D | 数据准备、文档与部署配合 | 演示数据、设计文档、运行说明和演示脚本 |
| 本助手 | 主要实现与集成 | 小步可运行代码、测试、变更说明与修复 |

这些是职责建议，B、C、D 也可以用各自助手完成独立页面、测试或文档，再由对应成员复核。不能把“已让 AI 生成”作为完成标志。每位成员都应能够解释需求、状态、测试和自己的贡献。

GitHub 建议：保持主分支可运行；每个任务说明需求编号、范围和验收条件；使用短分支和小 PR；至少一名其他成员复核；涉及订单、状态、权限、数据库迁移的改动由主工程实现统一整合。AI 创建分支按仓库约定使用 `codex/` 前缀。

本次仅编写方案，尚未创建 GitHub 任务、分支或 PR，也未联系其他成员或助手。

### 6.2 第 1 周：需求基线与最小闭环

**第 1—2 天：**每人访谈约 2 位有校园闲置交易经历的同学，记录事实和原话；另向老师确认认证、流转、交易与验收边界。完成两个项目的需求分析与比较，登记假设、待确认问题、来源和优先级。

访谈重点包括如何发布与找物品、怎样约定交付、遇过哪些取消或纠纷、最需要记录什么。不要把“你是否喜欢这个平台”作为唯一问题。

**第 3—4 天：**冻结首版范围、角色权限、关键状态；画用例图、商品／订单状态图、主要页面草图和 ER 图；为每条核心需求写验收条件。

**第 5—7 天：**完成注册登录与人工认证、商品发布审核、公开浏览，以及最简预约到双方交付确认。先做纵向闭环，再补全外围功能；补上重复下单和对象权限的基础测试。

**周验收：**两位演示用户可完成一笔交易；未认证用户不能下单；无关用户不能操作订单。若闭环未通过，立即停止扩展功能，集中修复。

### 6.3 第 2 周：覆盖课程全部核心类别

完善搜索筛选、收藏咨询、取消释放、商品关键修改重审、订单约定和历史记录；补上评价举报、管理员限制与基础统计，使十类功能均有可演示路径。

同步完成架构说明、数据库约束、权限矩阵、创建订单与交付确认时序图，以及需求到测试的对应表。

**周验收：**十类功能能逐项演示；正常交易、取消交易、拒绝审核和举报处理各通过一次；明确部署数据库并完成对应环境的核心交易验证。未通过时，删减体验扩展，不删课程核心类别或关键权限。

### 6.4 第 3 周：测试、修复与部署验证

完善关键自动化测试并开展多人交叉验收，重点检查并发预约、重复提交、越权、状态冲突、封禁后的在途订单和举报暂停流程。

完成图片限制、错误页面、基础移动端适配和性能测量。在选定环境走通安装、迁移、管理员创建、静态资源、图片保存与访问，以及数据库和图片备份恢复。

如果需要公网部署，在实际对外开放前确认部署环境、域名、访问范围和真实数据使用；不要把开发服务器直接当作公网交付环境。

**周验收：**没有尚未解决的重复成交、数据丢失、越权或主流程阻断问题；另一位成员可依据说明从干净环境运行；已实际验证备份恢复。剩余问题按影响登记。

### 6.5 第 4 周：冻结、复核与答辩

第 22 天起冻结功能；只修复缺陷、补验收证据与必要文档，不加入 AI 推荐、实时聊天或新交易模式。

对需求表逐条回归，完成测试报告、已知限制、用户手册、运行与部署说明。使用稳定的虚构数据演练答辩，至少进行一次由非主要开发成员操作的完整演示。

**最终验收：**交付物能够互相对应；从需求编号可以找到页面、规则和测试；四人能够解释各自贡献和主要设计；运行步骤可复现，已知限制如实说明。

### 6.6 进度失控时的调整顺序

优先取消装饰性图表、消息提醒、复杂排序和自动超时，保留普通列表、手动刷新和明确取消。其次缩小图片数量与统计维度。始终保留课程十类功能的基础实现、权限、订单唯一性、双向交付确认及关键测试。

若第 1 周无法跑通闭环，或第 2 周仍缺少多个核心类别，应由团队重新评估投入与老师验收要求；不能用一个仅有页面的原型宣称完成系统。

## 7. 测试与验收清单

| 场景 | 预期结果 |
| --- | --- |
| 未认证用户发布／下单 | 服务端拒绝；无业务记录产生 |
| 审核前访问商品公开链接 | 不泄露未批准内容 |
| 卖家给自己下单 | 拒绝 |
| 两用户同时预约同一物品 | 最多一个有效订单；商品和订单一致 |
| 连续重复点击下单／确认 | 不创建重复交易，不重复计数 |
| 修改他人商品／读取他人订单和咨询 | 拒绝，并且不返回私密内容 |
| 取消有效订单 | 记录原因；允许售卖时释放物品 |
| 商品被管理下架后取消订单 | 保持不可售，不能自动上架 |
| 只有卖家或买家确认交付 | 仍待交付 |
| 双方确认交付 | 完成一次，商品成交，保留确认时间 |
| 一方确认后尝试单方取消 | 拒绝并提供争议入口 |
| 存在交付争议时确认完成 | 暂停终态变更，等待处理 |
| 非参与者评价／重复评价 | 拒绝；参与者完成后可各评价一次 |
| 用户被限制后处理已有订单 | 可访问必要订单并按规则处理，不能新下单 |
| 上传不支持文件／超出限制 | 明确拒绝，不留下不完整业务记录 |
| 统计核对 | 取消不计成交，完成记录与汇总一致 |
| 备份恢复 | 商品、交易及其图片恢复后可查看 |

开发时使用项目现有 Django 检查、测试、Ruff 检查和格式检查。并发测试应使用适合验证真实事务的方式，在目标数据库上执行，不能只依赖普通顺序请求或一个被测试框架包裹的事务。

验收证据应写明环境、数据规模、操作步骤、预期、实际、日期和版本。此清单是未来测试计划，本次尚未实现业务或执行这些测试。

## 9. 供团队评估的决策点

评估时优先确认：

- 是否接受“课程十类功能全部覆盖，但每类采用基础实现”的首版范围？
- 是否接受单校园、单件出售、线下支付、私密留言和人工认证？老师是否认可？
- 是否接受“流转”先实现交易过程追溯，而不做再次转卖谱系？
- 是否能在第 2 天前明确取消、交付争议、审核和认证规则？
- 四位成员是否能承担需求复核、页面验收、测试与交付，而不仅是等待 AI 输出？
- 是否能在四周中安排每周可运行演示，并在最后一周停止加功能？

### 11.5 GitHub 任务包与工程交接

以下是可录入 GitHub 的任务设计，尚未创建远程任务或改动仓库设置。

| 任务包 | 依赖 | 范围与交付条件 | 人类复核负责人 |
| --- | --- | --- | --- |
| GH-01 双项目需求基线 | 无 | 两套分析、DEC 清单、首版范围及 TR 验收条件可评审 | A |
| GH-02 页面与数据设计 | GH-01 | 页面流程、状态、权限和数据关系一致 | B；A 复核规则 |
| GH-03 账号与商品入口 | GH-02 | TR-01 至 TR-03 主路径可运行，权限测试通过 | B；C 复核 |
| GH-04 交易核心 | GH-02，集成需 GH-03 | TR-05、TR-06、TR-09；重复预约、取消和约定版本可验证 | C |
| GH-05 辅助业务与管理 | GH-03，部分依赖 GH-04 | TR-04、TR-07、TR-08、TR-10 均有正常和拒绝场景 | B；C 复核 |
| GH-06 集成与环境验收 | GH-03 至 GH-05 | 自动检查、跨成员回归、备份恢复和运行说明一致 | C、D |
| GH-07 文档与答辩 | 从 GH-01 起持续更新；最终依赖 GH-06 | 设计、需求与实际软件一致，四人演练通过 | D；全员复核 |

本助手主要实现 GH-03 至 GH-06，并细化 GH-02 的技术设计；其他成员及助手可以承接独立子任务。任何子任务开始前应确定范围、文件或模块边界、依赖、验收条件和负责人。用户、订单核心模型与数据库迁移采用单一整合负责人，避免多个助手各自修改后才发现冲突。

每个 PR 写明：关联任务与需求编号、实际变更、验证命令及结果、已知限制。由至少一名其他成员审查；合并后重跑核心交易回归。AI 协助生成的内容在贡献记录中如实标明，具体披露格式遵循课程要求；不能虚构人工贡献。

“由本助手承担主要工程”按对话中的具体任务逐批推进：接收范围 → 实现 → 检查 → 提交可审查结果 → 团队复核。当前没有启动四周后台执行或定时任务。各成员助手之间也未建立自动通信；需要交接时，用任务说明、PR 和共享文档传递上下文。

需求变更统一记录提出者、理由、影响需求、工作量和验收条件。冻结后新增功能先做取舍：说明替换哪项工作或怎样增加时间，不能只修改页面而遗漏测试、设计和文档。

### 11.6 风险触发条件与完成标准

| 风险 | 触发证据 | 处理动作 |
| --- | --- | --- |
| 课程理解偏差 | DEC-01 至 DEC-03 的默认范围被否定 | D2 优先调整需求，不继续按旧范围开发 |
| 投入不足 | 四人可投入总量低于预算，或周里程碑未通过 | 重估剩余量，先取消体验深化，保留核心类别 |
| 多助手产生冲突 | 同一模型、迁移或核心规则出现两套实现 | 统一负责人，以冻结规则和验收案例裁定 |
| 只验收成功场景 | 功能演示通过但无权限、取消和并发证据 | GH-06 不通过，先补关键拒绝和异常场景 |
| 环境迟迟不确定 | D4 后仍无法确定交付方式或目标数据库 | 先落实受控演示环境；新增部署要求重新估算 |
| AI 代码与文档不一致 | 人工操作、测试与说明得到不同结果 | 以确认后的需求为准修复，实现后同步文档 |

单项任务完成需要同时满足：验收条件达成；关键规则有适当测试或明确人工证据；相关文档同步；变更可审查；没有本任务生成的无用临时文件。仅生成代码或提交 PR 不能视为验收完成。

整体验收的建议门槛是：十类核心功能逐项通过；自动检查通过；无未解决的越权、重复成交、数据丢失或主流程阻断缺陷；成员能从干净环境复现运行；备份恢复实际演练；遗留问题和课程确认结果可查。是否满足课程最终评分要求仍以老师为准。
