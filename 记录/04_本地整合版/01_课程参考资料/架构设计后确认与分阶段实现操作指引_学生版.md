# 架构设计后确认与分阶段实现操作指引（学生版）

适用：《软件工程》课程各项目组；日期：2026-11-09。  
用途：把AI辅助产生的架构讨论稿转化为可实施、可审查、可验证的开发基线。

## 一、流程总览

架构讨论稿 → Q澄清 → ADR评审 → 同步需求与架构 → 细化当前阶段接口及关键设计 → 准备测试依据与任务 → 阶段准入 → 编码、审查与测试 → 阶段验收 → 下一阶段 → 部署验收。

不要等全部代码完成才测试，也不要为了开始开发而一次性细化全部接口。可以滚动细化，但跨模块共享契约及当前阶段依赖必须先确认。

| 角色 | 主要责任 |
| --- | --- |
| 组长/基线维护人 | 汇总问题、安排评审、维护版本和任务依赖 |
| 业务确认人 | 确认范围、规则及预期结果；模拟角色必须注明 |
| 模块负责人 | 细化接口、数据和实现，提交测试证据 |
| 交叉审查人 | 核对变更、验证结果，不能由AI替代 |
| 教师/助教 | 确认课程范围和验收口径，处理关键争议 |
| AI | 提出候选、检查影响、草拟文档/代码/测试；无最终确认权 |

四人组可兼任角色，但关键变更由另一成员复核。不是每项技术选择都需教师审批，业务歧义和课程范围变更才应升级确认。

## 二、建立一个清晰的文档入口

建议沿用现有目录，仅增加以下文件；已有同等文档时链接复用，不重复维护。

```text
项目目录/
  需求规格说明书.md                  # 使用项目已有真实文件名
  软件架构设计方案_讨论稿.md          # 保留原稿
  软件架构设计方案_基线版.md
  架构确认与决策记录.md              # 集中维护Q和ADR
  接口与关键设计说明书.md
  分阶段实现与测试计划.md
  tasks/                           # 阶段任务卡，可改用Issue
  evidence/                        # 精选测试与审查证据
```

Git保存文档和代码版本；Issue保存任务状态；正式决定不能只留在聊天。聊天记录无需全文提交，保留影响关键决定的片段及证据即可。

## 三、步骤1：整理Q并确定阻塞范围

**主导：基线维护人；辅助：模块负责人、AI。**

1. 从架构稿抽取全部Q，保留原编号。
2. 区分业务规则、技术条件、范围及验收问题，指定真实责任人。
3. 标出影响任务；不相关任务可继续，相关任务不得靠AI猜测推进。
4. 列出选项、代价与推荐，不把推荐当决定。

### 模板A：Q确认与关闭记录

| 字段 | 填写内容 |
| --- | --- |
| Q编号/标题 | Q-__ / __ |
| 冲突及依据 | 需求编号、章节、原描述 |
| 备选及影响 | 方案A：__；方案B：__ |
| 最终决定 | 用可以检验的规则表达，不能只写“按建议” |
| 确认身份 | 姓名、角色、真实确认/教学模拟、日期 |
| 业务依据 | 任务书、访谈、制度或明确的教学设定 |
| 阻塞范围 | 哪些任务不能开始；哪些仍可继续 |
| 需同步资产 | 需求、状态图、ADR、接口、数据约束、测试 |
| 验证场景 | 正常、边界、异常各如何判断 |
| 状态 | 待确认/已决定待同步/已关闭/已重新打开 |
| 关闭证据 | 文档位置、版本、交叉复核人 |

示例：二手平台解冻时，若仍有有效订单则恢复预订，若仍有其他冻结依据则继续冻结，只有无有效占用且满足其他上架条件才恢复上架。**此处仅演示记录形式，具体规则仍需项目组确认。**

关闭标准：人已作决定，受影响文档已同步，预期可检验，另一成员已复核。回答了问题但没有同步文档，只能标“已决定待同步”。

## 四、步骤2：评审ADR

**主导：架构/模块负责人；决定：团队；辅助：AI、助教。**

1. 检查每项决策依赖的Q是否解决。
2. 对比备选方案，说明收益、代价和验证方式。
3. 标为已接受、已拒绝或暂缓；需要技术试验时先保持待验证。
4. 后续改变已接受方案，新增替代ADR并关联旧记录，不抹除历史。

### 模板B：ADR

```text
编号/标题：ADR-__ / __
状态：提议/待验证/已接受/已拒绝/暂缓/已被替代
背景：关联需求、Q及限制条件
比较：至少说明可行备选，不为凑数创造明显不适用方案
决定：采用什么，明确不采用什么
理由：与业务、团队、部署及测试条件的关系
代价：新增复杂度、限制及风险
验证：怎样检查该选择是否成立；结果/证据位置
确认：确认人、复核人、日期
重新评估条件：什么变化发生时需要重开
替代关系：替代ADR-__ / 被ADR-__替代
```

接受架构不等于性能已达标。高风险技术假设可用隔离的小型试验验证；试验授权、代码与正式实现区分，结果失败则更新ADR。

## 五、步骤3：将聊天决定落到仓库基线

**主导：基线维护人；复核：另一成员。**

可向AI发送以下模板：

```text
以下是人工确认结果，不是请你代替我们作决定：
Q-__：决定__；确认人__；身份__；依据__。
ADR-__：接受/拒绝/暂缓；理由__。
请先列受影响的需求、状态、数据、接口及测试，再更新相关文档。
保留原架构讨论稿，另存基线版。未确认项保持原状态。
如发现新矛盾，请列出问题，不自行补全。暂不生成实现代码。
输出变更摘要与待人工复核清单，不自行标记“人工已确认”。
```

人工查看文档差异，逐项核实决定是否准确落实；若改变了需求，按需求变更流程同步原基线的版本记录。之后按课程已有Git流程提交，登记提交标识。

### 模板C：基线索引

| 资产 | 路径/版本 | 状态 | 确认人 | 备注 |
| --- | --- | --- | --- | --- |
| 需求 | __ | 已确认范围/候选项分别说明 | __ | __ |
| 架构 | __ | 已接受ADR清单 | __ | __ |
| 接口 | __ | 当前阶段已冻结接口 | __ | __ |
| 测试依据 | __ | 已人工核验预期 | __ | __ |

本次基线提交标识：__；尚未解决Q：__；允许开始阶段：__；阻塞阶段：__。

不要伪造Git提交号。可在提交后通过Issue或后续索引更新记录真实标识，无须让一个提交的文件预先包含它自己的哈希。

## 六、步骤4：补齐当前阶段接口及关键设计

**主导：相关模块负责人共同；辅助：AI。**

先用“需求→业务动作→接口”矩阵检查遗漏，再逐接口细化。GET/POST等方法不能替代业务契约；同一路径不同方法也分别记录。

### 模板D：接口契约

| 项目 | 内容 |
| --- | --- |
| 接口编号/名称 | API-__ / __ |
| 需求与决策依据 | FR/BR/权限/状态转换/ADR编号 |
| 方法与路径 | __ |
| 调用者及权限 | 角色、对象归属、受限账号行为 |
| 请求 | 路径/查询/请求头/请求体分别列字段、类型、必填、范围、空值规则 |
| 成功响应 | HTTP状态、字段类型、业务状态及示例 |
| 失败响应 | 条件、错误码、字段、示例及数据是否改变 |
| 前置与后置 | 原状态、允许条件、成功后的业务不变量 |
| 并发与幂等 | 请求键、版本检查、重复请求、不同负载、竞争失败 |
| 事务 | 必须同时成功的数据变化，事务外副作用 |
| 隐私 | 各角色输出字段、禁止日志内容 |
| 测试关联 | TC-__ |
| 确认 | 提供方、调用方、复核人及版本 |

每个关键写接口至少给出正常、业务失败、重复请求示例。查询接口说明分页、排序、过滤和数据范围。

关键详细设计只聚焦难点：状态转换表、数据库唯一约束、锁顺序、事务边界、超时重试、异常恢复、规则版本。不要让前端、后端各自猜字段或让不同AI任务自行决定错误语义。

## 七、步骤5：先准备测试依据，再拆阶段任务

**主导：测试责任人；确认：业务责任人；辅助：AI。**

预期结果应来自原始任务书、已确认需求、人工业务走查和规则，不仅来自实现或AI生成的需求。AI可以扩展案例，不能独自确认业务正确。

### 模板E：测试案例

| 字段 | 内容 |
| --- | --- |
| 编号/关联依据 | TC-__；需求/规则/外部确认记录__ |
| 层级 | 单元/数据库集成/接口/端到端/性能 |
| 场景和风险 | __ |
| 前置数据与角色 | 使用合成数据；__ |
| 操作/输入 | __ |
| 预期结果 | 输出、数据库状态、不得发生的变化 |
| 预期确认人 | __，日期__ |
| 执行结果 | 未执行/通过/失败/阻塞 |
| 证据 | 代码版本、环境、命令、原始结果位置 |

并发不变量必须用真实数据库多连接验证；顺序调用和内存Mock不能证明并发正确。外部模拟测试不能声称真实校园服务集成通过。

### 模板F：阶段计划

| 阶段 | 可运行业务链 | 需求范围 | 前置Q/ADR | 接口 | 必测风险 | 退出条件 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | __→__→__ | __ | __ | __ | __ | 可演示、测试通过、审查完成 |
| S2 | __→__→__ | __ | __ | __ | __ | 同上，并通过S1回归 |

二手平台示例：发布审核查询→下单及取消→交付确认评价→退货纠纷治理；自习室示例：资源查询预约→签到暂离释放→信用申诉→候补管理报表。实际顺序按依赖调整，不能借分阶段遗漏已批准范围。

### 模板G：Issue或本地任务卡

```text
任务编号/名称：TASK-__ / __
负责人/审查人：__ / __
关联阶段、需求、ADR、接口和测试：__
目标：一句话说明可观察业务结果
输入基线：文档路径、版本或提交标识
允许修改：模块/文件范围
禁止修改：范围外模块、未批准规则、验收预期等

停止条件：需改需求/接口/架构或新增依赖时先反馈
状态：待准备/可开始/实现中/待审查/需修改/已完成
```

## 八、步骤6：阶段准入检查

组长和审查人共同确认，以下关键项不满足则暂停对应任务，而不是停止整个项目：

- [ ] 阻塞本阶段的Q已关闭，相关ADR已接受。
- [ ] 提供方与调用方确认接口、状态及错误语义。
- [ ] 数据不变量、事务和权限边界明确。
- [ ] 测试预期已经人工核验，必要测试数据可用。
- [ ] 环境、启动说明、配置和密钥管理方式明确。
- [ ] 任务负责人、审查人、允许修改范围及完成条件齐全。

批准开始：阶段__；任务__；批准人__；日期__；已知非阻塞限制__。

## 九、步骤7：小步编码、审查和测试

1. 学生让AI先读取任务与基线，输出执行计划和疑问，不立即扩大范围。
2. 学生核对计划，批准一个小任务；按课程Git约定使用任务分支，避免多人直接改同一基线。
3. AI辅助实现与编写测试；学生检查关键业务逻辑、权限、事务和迁移。
4. 运行任务测试及受影响回归；记录真实命令、环境、版本和结果。
5. 学生查看diff，另一成员审查；通过后按既有流程合并。
6. 更新任务和文档，开始下一个小任务。不让AI自行宣布阶段验收完成。

### 可直接使用的编码提示模板

```text
请读取TASK-__及其引用基线，仅处理该任务。
先给出计划、修改范围、风险和测试安排，发现未决规则先提问。
批准后才实现；不要改变验收预期、删除约束或添加未批准功能。
完成后提供diff摘要、真实测试结果、未运行项及原因。
涉及跨模块接口、数据库迁移或新依赖时先请求人工评审。
```

### 模板H：审查与测试记录

```text
任务/提交标识：__
实现者/审查者：__ / __
需求和契约是否满足：__（证据位置）
权限、事务、并发、幂等是否检查：__
测试命令/环境/结果位置：__
未执行及阻塞：__
发现问题和处理：__
文档是否同步：__
结论：通过/需修改/待核验
```

测试失败先判责：实现不符则修实现；测试预期错误需依据及人工批准后修测试；需求冲突则重开Q。禁止仅为“全绿”删断言、绕过权限或硬编码返回值。

## 十、步骤8：阶段验收、变更及最终部署

每阶段进行短验收：演示一条完整业务链，抽测一个关键异常，核对测试结果和diff，确认没有未处理的严重问题；前阶段回归也必须通过。证据不足标待核验，不凭截图声称已验证。

### 模板I：阶段验收单

| 项目 | 记录 |
| --- | --- |
| 阶段/版本/环境 | __ |
| 完成需求与未完成项 | __ |
| 主流程演示及异常场景 | __ |
| 自动测试和人工检查证据 | __ |
| 相关Q/ADR/接口是否有变更 | __ |
| 残余风险与阻塞下一阶段事项 | __ |
| 结论/验收人/日期 | 通过/整改/待核验；__ |

新发现的问题使用变更记录：“原因→影响需求/ADR/接口/数据/测试→人工决定→修改→回归”。重大架构变化新建ADR，旧ADR标记被替代；原文档通过Git或独立版本保留。

全部阶段完成后才做最终部署验收：按说明从干净环境启动，执行全链路及权限回归，测试真实数据库、媒体访问、外部故障恢复、备份恢复和获准负载。性能阈值先确认，不能测试后再选择有利指标。

## 十一、测试时间安排速查

| 时点 | 做什么 | 产出 |
| --- | --- | --- |
| 架构确认时 | 状态/权限/事务场景走查，必要技术验证 | 问题与ADR验证记录 |
| 当前任务编码前 | 独立确认测试预期和数据 | 测试案例 |
| 编码过程中 | 单元、接口、数据库集成测试 | 脚本与原始运行结果 |
| 每次合并前 | diff审查和受影响回归 | 审查记录 |
| 每阶段完成 | 纵向链路、异常和跨模块验证 | 阶段验收单 |
| 最终部署后 | 系统、性能、安全边界及恢复验收 | 最终测试与部署证据 |

## 十二、需提交最小材料包

1. 一个入口：基线索引，包含版本、范围和未决问题。
2. 一份确认记录：Q结论、ADR及人工责任，不交大量聊天截图。
3. 当前阶段接口与关键设计：足以让不同成员独立实现并对接。
4. 阶段计划与任务卡：能查到需求、实现及测试关联。
5. 精选证据：关键并发/权限/异常测试、交叉审查、阶段验收和AI纠错案例。


**阶段开始看“依据是否明确”，阶段完成看“实现与证据是否一致”。AI可以承担大量生成工作，但业务确认、架构取舍和验收责任必须落实到人。**
