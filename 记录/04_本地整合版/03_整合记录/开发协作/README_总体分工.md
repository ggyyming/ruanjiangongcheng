# 校园物品流转市场：开发总体说明

版本：1.0；编制日期：2026-10-29；阶段：开发任务规划，尚非开发完成报告。

## 1. 这次要交付什么

最终提交一个能从干净目录安装、初始化并启动的完整 Django 项目，以及对应的环境清单、运行说明和验证记录。三位成员分别开发三个业务包，当前对话中的 Codex 负责统合三人的结果；用户负责协调、提供分支/PR和组织实际人工验收。集成工作不额外占用一个成员开发包。

目前仓库只有 Django 工程底座与 `/health/` 检查入口，校园市场业务尚未实现。附件中的可点击原型是需求表达材料，不能当成最终系统。Python/Django 项目没有单独的前端编译流程；“可编译运行”在本项目落实为依赖可安装、迁移可执行、检查和测试通过、浏览器能够操作完整业务。若教师另有指定打包格式或技术栈，先补充要求再调整。

## 3. 三份任务

| 工作包 | 主责成员 | GitHub 账号 | 负责交付的完整功能 | 分支前缀 |
|---|---|---|---|---|
| A | 待填写 | 待填写 | 注册登录、校内认证审核、物品发布审核、公开浏览、隐私权限、公共页面基础 | `codex/a-` |
| B | 待填写 | 待填写 | 多人申请、单人预留、三类交付、取消撤销、模拟支付/退款/结算、24小时付款处理 | `codex/b-` |
| C | 待填写 | 待填写 | 借用期限、归还、延期、逾期限制恢复、损坏丢失争议、站内通知 | `codex/c-` |
| 集成 | 本对话 Codex | 用户提供仓库入口 | 合并、联调、全量测试、环境复验、提交打包和缺陷归属 | `codex/integration-` |

三份按业务边界划分，各自包含模型、迁移、表单、页面、业务逻辑、测试、运行说明。不是把三个人分成“只写前端、只写后端、只写报告”，也不是各自另建一个完整网站。B 状态和资金规则最多，应分成小 PR 尽早联调；C 同时承担跨业务的通知能力，A 尽早交付底座支持另两位开工。

成员姓名不自动套用需求分析阶段的贡献表；由用户将实际承担开发的三人填入上表。

## 4. 需求依据与实现范围

唯一业务依据是本主题的 [需求规格说明书](../需求规格说明书.md)，配套使用 [业务细则 CP-D-01～23](../附件/01_规则与数据/业务细则确认记录.md)、[状态转换说明](../附件/01_规则与数据/状态转换说明.md)、[需求追踪矩阵](../附件/01_规则与数据/需求追踪矩阵.md) 和 [场景走查记录](../附件/03_场景与原型/场景走查记录.md)。不得把 `docs/需求文档智能审查系统/` 的功能做进来，也不得拿上级目录的旧联合稿覆盖本主题新细则。

开发沿用 Python 3.13、Django 5.2、SQLite、uv、Ruff。建议采用 Django 模板和普通表单完成网页交互，不新增独立前端工程、Redis、Celery 或真实支付依赖；需要新增依赖时先说明理由，由集成者协调锁文件。

最终应覆盖 27 条需求及 CP-D-01～23。支付、退款、结算仅做可持久化、可测试的模拟服务，明确显示“模拟”，不接真实收付、不收集真实身份资料、不设置钱包。阶段开发顺序不等于删减最终范围。功能未实现或验收未通过时必须如实登记，不能用“原型已看过”代替测试。

## 6. 按交付门槛推进

| 阶段 | A | B | C | 集成验收门槛 |
|---|---|---|---|---|
| M0 接口与骨架 | 公共模板、用户与认证接口、物品模型初始迁移 | 申请/流转模型及服务签名初始 PR | 借用/争议/通知模型及接口签名初始 PR | 三包在同一 main 上安装、导入、迁移、基础测试通过 |
| M1 第一条闭环 | 认证与物品审核可用 | 赠送：申请→预留→双确认 | 通知入口与借用约定 | 浏览器走通赠送，越权被拒绝 |
| M2 三类正常流程 | 补全发布重提和权限 | 买卖模拟支付和结算、借出支付/交付 | 正常借还、押金约定、退款触发 | 买卖、赠送、借还三条实际数据库流程通过 |
| M3 异常规则 | 撤销资格、重审核、隐私回归 | 取消撤销、超时、迟到支付、资金失败和重试 | 延期、逾期、损坏丢失、全部恢复 | CP-SC-01～11 及新增细则测试通过 |
| M4 最终提交 | 修复 A 缺陷、交接说明 | 修复 B 缺陷、交接说明 | 修复 C 缺陷、交接说明 | Codex 从干净目录复验、生成实际环境清单和项目包；用户做人工验收 |

M0 的模型依赖顺序是 A0 用户/物品 → B0 申请/流转 → C0 借用/争议/通知；完成三包骨架后再联通双向业务调用。B0 只先交供 C 引用的流转模型，不要求 C0 先存在才能创建该模型。三位成员可同时设计自己的表单和测试；跨包测试在依赖合并前可隔离运行，但不得把隔离测试称为联调通过。不能让 B/C 长期复制 A 的模型或临时自造用户系统，也不要等三个人全部开发完才第一次合并。

## 7. 完成的定义

每包完成 = 功能和页面可操作 + 数据持久化 + 迁移入库 + 核心规则测试通过 + 没有跨包私改 + PR 和交接记录齐全。项目完成 = 三包集成后通过下述最终验收，并产出匹配同一提交版本的环境清单和完整项目文件。

当前没有创建远程 Issue、分配真实账号、推送分支或运行完整业务验收。本目录是可以直接交给三位成员及其 AI 的开发协作材料。

## 8. Codex 的统合责任与最终验收

用户将三人的实际分支/PR或完整交付文件，以及各包交接记录提供到本对话后，由 Codex 继续统合。Codex 不会自动获得其他成员私有聊天或电脑里的代码；本轮也未启动三位成员的开发。

统合负责：核对共同约定和代码差异、按依赖顺序合并模型与迁移、处理配置/路由/模板冲突、补跨包测试和统一调度命令、整理演示数据初始化、运行说明、最终环境清单和完整项目包。公共依赖改动在集成中统一更新 `pyproject.toml` 与 `uv.lock`。各成员仍负责自己包内缺陷的修复和说明。

最终必须交付：

- 完整源码、项目配置、依赖清单及锁文件、全部应用迁移、模板和静态资源、测试、必要的虚构演示素材；不依赖某个人电脑中的数据库或绝对路径。
- `README.md`：从干净目录安装、迁移、初始化虚构数据、启动网站、执行定时扫描和测试的实际操作。
- 环境清单：实测系统、Python/uv/Django/SQLite/Ruff/Git版本、直接和锁定依赖、端口、数据库位置、模拟支付方式、上传目录及调度方法；记录复验日期和对应提交号。
- 验收记录：27条需求及CP-D-01～23对应测试/人工检查、CP-SC-01～11完整流程、真实结果和遗留项。历史原型反馈不算本次系统验收。
- 从最终版本导出的完整项目文件及版本标识，附干净环境运行结果。虚拟环境、真实个人资料、密钥、缓存和临时数据库不作为项目依赖打包；演示数据用可重建方式交付。

最终基础检查：

```powershell
uv sync --frozen
uv run python manage.py migrate
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run python manage.py test
uv run ruff check .
uv run ruff format --check .
uv run python manage.py runserver
```

上列是最终复验流程，不表示已经对业务项目执行通过。虚构数据初始化、模拟回执及 `process_market_jobs` 的确切操作由统合阶段实现、验证并补入运行说明。验收必须从全新数据库重建，并在浏览器实际完成买卖、赠送、借还和关键异常，不能只看 `/health/` 返回正常。

当前环境基线（2026-10-29 本机读取，供三位成员对齐；不是最终提交环境认证）：Windows 11，Python 3.13.15，uv 0.12.16，Django 5.2.17，SQLite 3.53.1，Ruff 0.16.8，Git 2.55.0.windows.5。最终版本仍须在统合后重新采集和复验。
