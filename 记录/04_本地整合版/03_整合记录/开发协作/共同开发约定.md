# 三个开发包的共同约定

版本：1.0；2026-10-29。以下目录、对象名、函数签名是**本次建议的开发基线，尚未实现**。M0 由三位成员复核，交集成者登记采用的提交号后再作为代码契约；成员不能在自己的分支里单方面换成另一套。

## 1. 所有 AI 必须先读

先读仓库根 `AGENTS.md`、`README.md`、`docs/architecture.md`，再读本主题需求规格、CP-D 细则、状态说明、本人任务。以主题最新业务细则为准；发现矛盾时记录具体编号并向用户提出，不静默删规则。需求报告中历史原型的验证结论不能冒充新系统测试结果。

本项目是同一个 Django 单体网站。优先 Django 模板、Session 登录、Django Forms、ORM 和 SQLite；沿用 Django 内置 User，通过 `settings.AUTH_USER_MODEL` 关联，认证申请独立建表。不在三包之间传密码、共享数据库文件或各自引入 JWT/独立前端。不要另建根工程。

## 2. 文件与数据归属

| 所有者 | 主要路径 | 数据与责任 |
|---|---|---|
| A | `apps/accounts/`、`apps/catalog/` | 身份申请、审核历史、物品、内容审核历史、是否符合公开条件 |
| A | `templates/base.html`、`static/` 公共样式 | 公共导航和页面骨架；其余成员继承模板，扩展自有应用资源 |
| B | `apps/transfers/`、`apps/payments/` | 申请、唯一有效预留、流转、交付双方确认、取消/撤销/退回声明、模拟资金与重试记录 |
| C | `apps/loans/`、`apps/disputes/`、`apps/notifications/` | 借用约定/延期/归还/逾期限制、争议/履行/结束意见、站内通知 |
| 各包 | 自有应用的 `templates/<app>/`、`tests/`、`migrations/` | 页面、测试、迁移与模块说明 |
| 集成者 | `config/`、根 README、依赖锁、集成测试、交付材料 | 公共接线与整体运行；成员通过独立小 PR 提出必要修改 |

不要为遵守表格而提前生成大量空文件。M0 只创建实际依赖的模型和入口。注册 `INSTALLED_APPS`、根 URL、公共模板、依赖文件的修改在 PR 中单列，按集成顺序处理；其他成员同步 main 后再开发。迁移由模型所属成员生成；不得删除他人的迁移或以提供本地 SQLite 文件代替迁移。

建议对象名：A `IdentityApplication`、`Item`；B `Application`、`Transfer`、`PaymentOperation`；C `Loan`、`ExtensionRequest`、`Dispute`、`Notification`。一个被选中申请产生一笔 Transfer，借用 Transfer 对应一条 Loan；物品可有多次历史流转，但同时最多一笔进行中流转。

`Item` 保存公开信息和展示状态；预留关系与交付事实由 Transfer 保存，借用归还事实由 Loan 保存，资金事实由 PaymentOperation 保存。不要在三个表中各写一份互相矛盾的“交易完成”布尔字段。跨表状态在同一业务事务内协调，由拥有该表的服务执行。

## 3. M0 最小服务接口

Python 模块路径为 `apps.<app>.services`，以下统一使用关键字参数，模型主键使用 `*_id`，`actor` 为从服务端会话取得的当前用户对象。页面视图和其他包调用这些服务，不能直接替其他包修改业务状态。M0 补齐确切返回字段与枚举；不能只留下本文然后让成员猜。

| 所有者 | 建议签名 | 返回/契约 |
|---|---|---|
| A | `accounts.services.is_verified(*, user_id)` | bool；仅表示当前校内认证资格，不表示借用资格 |
| A | `catalog.services.can_display(*, item_id)` | bool；检查内容审核、下架和物主资格，不能据取消动作无条件公开 |
| A | `catalog.services.change_availability(*, item_id, available, reason)` | 返回 Item；仅由获授权业务服务调用；available=True 仍校验公开条件，历史不改写 |
| B | `transfers.services.apply(*, actor, item_id)` | Application；调用 A 认证与 C 借用限制检查，自有物品/不可申请状态拒绝 |
| B | `transfers.services.reserve(*, actor, application_id)` | Transfer；物主选择一人，原子关闭同轮其他申请，借用选择时再次检查资格 |
| B | `transfers.services.confirm_delivery(*, actor, transfer_id)` | Transfer；记录本人确认，支付/期限条件满足才允许，单方不完成 |
| B | `transfers.services.cancel_before_delivery(*, actor, transfer_id, reason)` | Transfer；双方均未确认交付方可用；退款通过资金服务处理 |
| B | `transfers.services.close_pending_loan_applications(*, user_id, reason)` | 关闭数量；仅关闭未被选择的借用申请，不动买卖/受赠/已预留 |
| B | `payments.services.is_paid(*, transfer_id, purpose)` | bool；purpose 为货款或押金；依据持久化成功结果，不能信任浏览器声明 |
| B | `payments.services.request_refund(*, transfer_id, reason)` | PaymentOperation；服务内再次校验业务资格与幂等，不因重复调用重复退款 |
| C | `loans.services.can_borrow(*, user_id)` | bool；仅判断本项逾期限制；A 校内资格仍单独检查 |
| C | `loans.services.delivery_ready(*, transfer_id)` | bool；双方已确认归还时刻和押金金额，金额须与 B 支付目标一致 |
| C | `loans.services.start_loan(*, transfer_id)` | Loan；B 借出双确认完成后调用，同笔重复调用不重复开借用 |
| C | `disputes.services.has_open_dispute(*, transfer_id)` | bool；B 在退款、结算和重试前查询 |
| C | `notifications.services.notify(*, recipient_id, transfer_id, event_key, message)` | Notification；transfer_id 可为空以支持身份/审核通知，event_key 唯一标记同一事件与接收人，重复执行不重复发 |

以上仅列跨包最小依赖。延期、争议关闭、撤销协商等操作在所属包内设计，不为它们额外建立通用工作流框架。普通违规操作建议使用 Django `PermissionDenied` / `ValidationError`，视图转换为明确拒绝页面或表单错误；拒绝不得留下半笔业务数据。跨包不得用 `except Exception: pass` 或“导入失败当作已支付/无争议”绕过依赖。

B 的业务编排可调用 C；C 的归还/争议结束编排可请求 B 退款。避免模块顶层相互导入导致启动失败，可在实际需要的服务函数内导入；模型关系使用字符串外键。整个过程仍是一条同步服务调用链，不加入消息总线。M0 用启动、迁移和服务集成测试验证循环依赖已解决。

## 4. 一致性和授权

- 写操作必须检查登录身份、参与资格、对象所有者/当事人/负责管理员和当前状态；隐藏按钮不能替代服务端授权。使用 POST 与 CSRF，GET 不改变业务事实。
- 只有预留后的当事双方能看联系方式和具体地点；身份资料仅申请人及负责审核管理员可见；争议材料仅双方及负责管理员可见。管理员不能因 `is_staff` 就查看所有私密材料；若使用 Django Admin，必须补对象和字段授权，不能直接注册敏感模型后默认全开放。
- 认证撤销阻止新增参与并下架未预留物品；已有流转继续履约。不得在归还入口重新套用“必须仍认证”而阻止归还。
- 物主选择申请人、双确认、取消及资金结果使用事务和条件更新/数据库约束防重。SQLite 不能单靠行锁保证唯一预留；以实际约束与竞争更新结果为准，冲突时拒绝并保持数据一致。
- 重复提交自己的确认幂等，不得替对方确认。协商撤销/争议期间按细则阻止新增交付或资金推进；已发出的资金请求仍记录实际结果。
- 资金金额统一十进制定点值，禁止浮点；已预留后固化本次价格/押金与双方约定，不因物品后续编辑变化。最低金额、字段长度、上传上限由相应包在 M0 提议并记录，不冒称需求已规定。
- 时间使用 Django 时区感知时间，页面统一北京时间。归还时刻“超过”才逾期，付款期限的边界按 CP-D-17 定义并测试；测试使用可控时间，不让大家等24小时。
- 资金支付、结算、退款各自保留处理中/未知/失败/成功和回执记录，不合并成一个完成状态。重试最多3次，不含首次；未知先对账，不能当失败盲目再发。
- 模拟回执只由受控模拟工具/管理命令产生，普通用户不能用 URL 参数直接写到账。金额、业务标识、用途与状态匹配后才能推进；所有页面醒目标注模拟。

## 5. 自动处理的运行约定

为保持课程环境简单，先用 Django 管理命令，不增加后台队列。B 提供 `process_payment_timeouts`、`process_payment_operations`；C 提供 `process_overdue_loans`。命令能重复执行，按当前持久化数据判断，不重复关闭申请、发通知或发资金请求。首次执行顺序、每条命令职责及参数必须写入模块说明。

集成者提供并验证统一 `process_market_jobs` 调度入口，顺序调用上述命令；它是最终验收所需交付物，当前尚未存在。自动恢复资格和符合条件后的退款应在相关状态变化时同步触发，命令扫描作为补偿，不要求用户手动点“恢复资格”。

演示时可明确运行一次扫描，独立运行环境用系统任务计划定期执行该统一命令。最终运行说明必须列出经过验证的调度方法和间隔，不能只启动网页就声称无人值守到期处理已运行。到期前提醒的具体时点/频率需求尚未给定，C 提出方案交用户决定；在确定前不宣称完整提前提醒已验收。

## 6. 页面与测试

建议路径归属：A `/accounts/`、`/items/`；B `/transfers/`、`/payments/`；C `/loans/`、`/disputes/`、`/notifications/`。每应用设置自己的 URL namespace。路径仅为本项目内部页面规划，不额外引入 REST API。公共导航由 A 维护；B/C 提交新增菜单需求给 A/集成者。

各包均需真实数据库测试：允许路径、拒绝路径、重复操作、跨对象越权和本包关键状态。跨包验收用集成后的真实服务，不以永久 mock 替代。材料记录统一写为“需求编号 → 测试模块/测试名 → 实际结果 → PR/提交号”；新结果不要写入历史 E-38～47 等旧证据。
