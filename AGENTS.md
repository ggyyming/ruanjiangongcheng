# AGENTS.md

This repository uses Codex as a coding agent. Follow these instructions when reading, editing, testing, or reviewing code in this project.

## Core Working Style

Prefer careful, minimal, verifiable changes over fast but speculative implementation.

Before making non-trivial code changes:

* Restate the goal in concrete terms.
* State important assumptions.
* Identify unclear requirements instead of silently guessing.
* Choose the simplest approach that satisfies the request.
* Push back if the requested change seems overcomplicated, risky, or unrelated to the actual problem.

For very small tasks, do not over-plan. Make the obvious minimal change and verify it.

## Simplicity First

Write the minimum code needed to solve the current task.

Before writing code, stop at the first option that fully satisfies the request:

1. Do not build it if it is unnecessary (YAGNI).
2. Reuse an existing helper, type, dependency, or project pattern.
3. Use the standard library.
4. Use a native platform feature.
5. Use an already-installed dependency.
6. Use a clear one-line implementation when it is sufficient.
7. Only then write the minimum new code that works.

Apply this ladder only after understanding the task and tracing the relevant flow. A small change in the wrong place is not a minimal solution.

Do not add:

* Unrequested features.
* Premature abstractions.
* Single-use frameworks or helper layers.
* Extra configurability that was not asked for.
* Defensive error handling for impossible or irrelevant scenarios.
* Broad rewrites when a local fix is enough.

If a solution is becoming much larger than expected, stop and simplify before continuing.

When a deliberate simplification has a real known ceiling, leave a short `ponytail:` comment naming the limitation and the condition that would justify upgrading it.

## Surgical Changes

Touch only the files and lines needed for the user’s request.

When editing existing code:

* Match the existing project style, naming, formatting, and structure.
* Do not refactor unrelated code.
* Do not rewrite adjacent code merely to make it look nicer.
* Do not change public behavior unless the task requires it.
* If unrelated problems are discovered, mention them in the final response instead of fixing them silently.

When your own changes create unused imports, variables, functions, files, or comments, clean those up.
Do not remove pre-existing dead code unless explicitly asked.

Every changed line should be traceable to the task.

For bug fixes, target the root cause rather than the reported symptom. Inspect the callers of the function being changed and prefer one correct fix at the shared boundary when the evidence supports it.

Do not simplify away input validation at trust boundaries, error handling that prevents data loss, security controls, accessibility basics, hardware calibration, or anything the user explicitly requested.

## Goal-Driven Execution

Turn requests into verifiable outcomes.

Examples:

* “Fix the bug” means reproduce or reason about the bug, make the smallest fix, then verify the fix.
* “Add validation” means define the invalid cases, add or update tests where appropriate, then implement validation.
* “Refactor” means preserve behavior, make the change in small steps, and verify before and after when possible.

For multi-step tasks, use a short plan like:

1. Locate the relevant code → verify by naming the files/functions involved.
2. Make the smallest necessary change → verify by reviewing the diff.
3. Run the most relevant checks → verify with tests, build, lint, typecheck, or a manual check.

## Testing and Verification

Prefer real verification over confidence.

After changes, run the narrowest relevant checks available, such as:

* Unit tests for the changed module.
* Type checking.
* Linting.
* Build command.
* A focused manual command that demonstrates the behavior.

Non-trivial logic should leave at least one small runnable check that fails when the behavior breaks. Trivial one-line changes do not need tests solely to satisfy this rule.

If tests or commands cannot be run, explain why and state what was verified instead.
Do not claim something works unless it was actually checked or can be directly inferred from the code.

## Final Cleanup

After coding, testing, building, or running debugging commands, check for temporary artifacts generated during the task.

Clean only files that are clearly generated by the current coding, testing, build, or debugging process, such as:

* test caches
* runtime logs
* temporary files
* debug output
* generated test reports
* local runtime data created only for this task
* screenshots, recordings, or mock data generated only for debugging

Do not delete:

* source code
* configuration files
* documentation
* dependency lock files
* committed fixtures
* migration files
* user-created assets
* files whose purpose is unclear

If unsure whether a file is safe to delete, do not delete it. Mention it in the final response instead.

Before reporting completion, run:

```bash
git status
```

## Communication Style

In final responses:

* Summarize what changed.
* Mention the files touched.
* Report verification results.
* Call out any remaining risks, assumptions, or follow-up tasks.

Keep explanations concise and practical.
Do not include long internal reasoning.
Do not present speculation as fact.

## When to Ask Before Editing

Ask for clarification before editing if:

* The task has multiple incompatible interpretations.
* The change could affect data loss, security, payments, authentication, deployment, or public APIs.
* The user’s request conflicts with existing project behavior or instructions.

If the ambiguity is small and the safe choice is obvious, proceed with the safe minimal choice and state the assumption.

## Project-Specific Commands

- Install dependencies: `uv sync`
- Run development server: `uv run python manage.py runserver`
- Run Django checks: `uv run python manage.py check`
- Run tests: `uv run python manage.py test`
- Run lint: `uv run ruff check .`
- Check formatting: `uv run ruff format --check .`
- Apply formatting: `uv run ruff format .`

## Source of These Rules

These instructions are adapted from the Karpathy Guidelines skill. The intent is to reduce common LLM coding mistakes: overcomplication, unnecessary rewrites, hidden assumptions, and unverified changes.
